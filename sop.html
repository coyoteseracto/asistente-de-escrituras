Sistema Integrado de Asistencia Lectora y Evaluación

Documentación Maestra, Estructura de Datos y Standard Operating Procedure (SOP)

1. Visión y Objetivos del Proyecto

El desarrollo de este sistema dota al semillero de escritura de una infraestructura técnica autónoma que automatiza la extracción, clasificación y consulta de figuras literarias, separando el análisis de obras canónicas de la evaluación de ejercicios estudiantiles.

  • Democratización del Análisis Estilístico: Proveer una biblioteca interactiva donde los estudiantes consulten cómo diversos autores emplean estructuras gramaticales complejas. La visualización superpone etiquetas dinámicas sobre párrafos inmutables (es decir, el párrafo puede contener varias figuras/estilos, estas coordenadas no se reeemplazan y se pueden llamar independientemente, el pasaje literario NO está condicionado por los hallazgos académicos, estos son capas sobre el texto original).
  • Evaluación Objetiva y Escalable: Integrar un bot de Discord que procese las entregas de los estudiantes y determine el cumplimiento de restricciones estilísticas.
  • Optimización de Costos y Cero Censura: Utilizar modelos abiertos (vía OpenRouter) para evitar censura en literatura, delegar enrutamiento a Cloudflare Workers, y mantener Supabase como almacenamiento privado.

4. Esquema Relacional de Base de Datos

Ubicación: /supabase/migrations/20261015_initial_schema.sql

Se separa físicamente la estructura del texto (Chunks) de la interpretación gramatical (Figuras). Este código se ejecuta mediante supabase db push.

-- Habilitar extensión vectorial para embeddings futuros
CREATE EXTENSION IF NOT EXISTS vector;

-- Tabla de Autores
CREATE TABLE authors (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name TEXT UNIQUE NOT NULL
);

-- Tabla de Obras
CREATE TABLE works (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    author_id UUID NOT NULL REFERENCES authors(id) ON DELETE CASCADE,
    title TEXT NOT NULL,
    entity_type TEXT CHECK (entity_type IN ('canonical', 'student')) NOT NULL DEFAULT 'canonical',
    UNIQUE(author_id, title)
);

-- Tabla de Bloques Inmutables (Mecanismo Estructural)
CREATE TABLE chunks (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    work_id UUID NOT NULL REFERENCES works(id) ON DELETE CASCADE,
    sequence_order INT NOT NULL,
    raw_text TEXT NOT NULL,
    embedding VECTOR(768)
);

-- Tabla de Anotaciones Semánticas (Mecanismo Semántico)
CREATE TABLE literary_figures (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    chunk_id UUID NOT NULL REFERENCES chunks(id) ON DELETE CASCADE,
    figure_type TEXT NOT NULL,
    matched_substring TEXT NOT NULL,
    explanation TEXT
);

-- Tabla de Entregas de Estudiantes
CREATE TABLE student_submissions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    student_discord_id TEXT NOT NULL,
    exercise_target TEXT NOT NULL,
    submitted_text TEXT NOT NULL,
    fulfilled BOOLEAN NOT NULL,
    analysis_json JSONB NOT NULL
);

5. Contrato de Respuesta JSON (OpenRouter)

Ubicación: /worker/src/openrouter.js

Esquema forzado que el Cloudflare Worker envía a la API de OpenRouter para garantizar que el LLM actúe como un etiquetador estricto y no devuelva prosa conversacional.

{
  "type": "json_schema",
  "json_schema": {
    "name": "literary_figures_extraction",
    "schema": {
      "type": "object",
      "properties": {
        "figures": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": {
              "figure_type": { 
                "type": "string",
                "description": "Clasificación gramatical o retórica." 
              },
              "matched_substring": { 
                "type": "string", 
                "description": "Cadena EXTRAÍDA LITERALMENTE del raw_text. Debe coincidir exactamente para permitir el indexOf() en el frontend." 
              },
              "explanation": { 
                "type": "string" 
              }
            },
            "required": ["figure_type", "matched_substring", "explanation"]
          }
        }
      },
      "required": ["figures"]
    }
  }
}

6. Standard Operating Procedure (SOP)

Rutinas operativas estándar para desarrollo e interacción en el sistema.

SOP-01: Ingesta Atómica y Fragmentación Estructural

Objetivo: Prevenir duplicidad y separar el texto físicamente sin depender de la gramática.

  1. El usuario selecciona Autor/Obra en el frontend. El sistema verifica contra Supabase.
  2. Si la obra no existe, se habilita el módulo de carga (.txt o .md).
  3. El script ingest.js en el navegador divide el texto basándose en delimitadores físicos (saltos de línea dobles \n\n).
  4. Los bloques generados se envían a Cloudflare, donde el Worker calcula el embedding vectorial y los almacena en la tabla chunks de Supabase.

SOP-02: Etiquetado Semántico Asíncrono

Objetivo: Identificar figuras literarias sin alterar el párrafo inmutable original.

  1. Los chunks sin procesar entran a una cola en el Worker de Cloudflare.
  2. El Worker envía el raw_text a OpenRouter utilizando el Contrato JSON estricto.
  3. El modelo retorna el tipo de figura y la matched_substring.
  4. El Worker inserta estos metadatos en la tabla literary_figures, vinculándolos al bloque correspondiente.

SOP-03: Visualización y Resaltado Dinámico

Objetivo: Superposición visual de análisis en la interfaz sin consumo de tokens.

  1. El usuario filtra por obra y tipo de figura literaria en el frontend.
  2. El Worker extrae de Supabase los chunks completos y sus etiquetas asociadas.
  3. El frontend renderiza el raw_text intacto.
  4. El script highlighter.js utiliza indexOf() sobre el texto renderizado para ubicar cada matched_substring y la envuelve dinámicamente con etiquetas <mark> para aplicar estilos CSS.

SOP-04: Evaluación en Discord

Objetivo: Validar ejercicios prácticos en el entorno del estudiante.

  1. El estudiante envía el texto mediante el comando /entregar-ejercicio.
  2. El Bot de Discord (bot.js) transfiere el payload al Worker de Cloudflare.
  3. El Worker solicita a OpenRouter una validación binaria (Cumple/No Cumple) basada en los parámetros del ejercicio y la extracción de figuras.
  4. Los resultados se guardan en student_submissions y se envían de vuelta a Discord en formato de tarjeta estructurada.

SOP-05: Administración Colaborativa y CI/CD

Objetivo: Sincronización entre administradores y agentes (Antigravity IDE).

  1. Todo el código reside en este repositorio central de GitHub.
  2. Los cambios a la base de datos se ejecutan estrictamente mediante supabase db diff y archivos de migración SQL. Prohibida la edición manual en el panel web.
  3. El desarrollo de agentes se basa en clonar el repositorio y leer los contratos JSON de este archivo.

SOP-06: Capa de Seguridad y Cero Leaks

Objetivo: Opacidad de infraestructura.

  1. Supabase rechaza conexiones directas públicas mediante políticas RLS.
  2. Las claves de API (OpenRouter, Supabase) residen únicamente en los secretos del entorno Cloudflare (wrangler secret put).
  3. El Cloudflare Worker realiza un proceso de sanitización eliminando UUIDs internos y vectores antes de retornar cualquier JSON al Frontend o a Discord.
